# 01 — Identity subuid/subgid mapping so the inner engine writes the same host uids as the host engine

Status: done

## Parent

None — no ADR covers UID mapping of the inner rootless engine. Needs a short
ADR as part of this issue (see `../NOTES.md` for incident, root cause and the
2026-09-14 experiment that proves the design).

## What to build

Today `Dockerfile` writes `node:100000:65536` to `/etc/subuid` and
`/etc/subgid`, so the inner rootless engine maps container uid N to host uid
`100000 + N - 1`. The host engine (Docker Desktop / native dockerd) maps 1:1.
Any Project state bind-mounted from the host (`./data/pgdata` …) therefore ends
up owned by a different host uid depending on which engine last wrote it, and
Postgres/MySQL/Redis refuse to start on the "wrong" side.

Replace the fixed range with an **identity mapping with a hole at the
Container user's uid `U`** (U = uid of the host user who launched boxa, which
is already what `node` is aligned to), generated by the entrypoint at every
Container start, before `start-rootless-docker.sh`:

```
node:1:(U-1)
node:(U+1):(65536-U)
```

For U = 1000 this yields the verified uid_map

```
0     1000   1
1        1   999
1000  1001   64535
```

Container uid 70 (postgres) → host 70, 999 (mysql/redis) → 999, i.e. exactly
what the host engine produces. Container root → U (unchanged, rootless cannot
map root → 0 and must not — boxa stays unprivileged). Container uid ≥ U is
shifted by one (U → U+1); document it, do not try to hide it.

Do not rely on anything in the Project's compose files; the mapping is a
property of the Container.

Migration: existing inner-engine storage (`boxa-<project>-docker` volume:
image layers, named volumes, container rootfs) was written under the old
mapping, so files that were container uid N are host uid `100000+N-1` and
become `nobody` under the new mapping. Handle it explicitly: detect the old
mapping marker (e.g. `/etc/subuid` content or a version stamp in the docker
volume), and on first start with the new mapping either (a) remap the whole
inner data-root once (`chown` walk from old range to new, run as Container
root, with progress output), or (b) refuse to start the inner engine and tell
the user to run `boxa stop --clean <project>`. Prefer (a) if the walk is
bounded (data-root sizes are typically < 20 GB); (b) is the acceptable
fallback for the first release, as long as the message is explicit.

Security note for the ADR: the boundary is the Container's mount namespace,
not uids. Container root already runs identity-mapped as uid 0 and can write
any uid into the bind-mounted Project and boxa volumes; letting the rootless
engine emit low uids there gives the inner processes nothing new. No
privileges, capabilities or host changes are added.

## Acceptance criteria

- [x] Fresh Container: `/proc/<dockerd>/uid_map` and `gid_map` show
      `0 U 1`, `1 1 U-1`, `U U+1 65536-U` for the actual launching uid U.
- [x] `docker run --rm -v <project>/tmpdir:/x alpine sh -c 'touch /x/f && chown 70:70 /x/f'`
      inside the Container yields host owner `70:70`; `999:999` likewise.
- [ ] `postgres:16-alpine` started inside the Container on a bind-mounted
      pgdata produces `70:70` files; the same pgdata then starts under the
      host engine, and starts again inside the Container, with data intact
      (the 2026-09-14 experiment sequence in `../NOTES.md`).
- [x] Nested overlayfs is not introduced: the inner data-root stays inside the
      `boxa-<project>-docker` volume (a data-root on the Container's overlay
      rootfs fails with `EINVAL` on overlay mount — observed in the
      experiment).
- [x] Existing Projects with old-mapping storage get the migration path
      (remap or explicit `boxa stop --clean` instruction); no silent
      `nobody`-owned image layers.
- [x] ADR added; `docs/docker-in-docker.md` documents the mapping, the
      root → U and U → U+1 caveats.
- [x] Unit test for the range generator (U=1000, U=501, U=65000 edge; sums
      to 65535 and never contains U or 0).
