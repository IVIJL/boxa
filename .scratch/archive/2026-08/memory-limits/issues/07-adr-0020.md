# 07 — ADR 0020: Per-project memory limits enforced on the outer Container

Status: done

## Parent

None — this issue creates the ADR.

## What to build

Write `docs/adr/0020-per-project-memory-limits.md` in the established ADR
style of `docs/adr/`, recording the decisions and the measurements behind
them (all verified on the target Docker Desktop/WSL2 host during the
design session):

- **Enforcement point is the outer Container's cgroup.** The inner
  rootless dockerd runs with `CgroupDriver=none`, so nested DinD
  workloads count against the outer limit automatically — and per-nested
  attribution is impossible in principle; everything is a project
  aggregate.
- **Derived default (65 % of host MemTotal), printed at startup.** A
  fixed-GB default is wrong on half of all machines; printing the
  effective value is what makes a default on existing projects
  acceptable. Per-project limits are caps, not reservations — not a
  global budget: N projects can still jointly exhaust the VM (accepted;
  a shared parent cgroup is not reachable under Docker Desktop).
  Mitigations, not guarantees: the sum > MemTotal joint-exhaustion
  warning at start (issue 01) and the documented `.wslconfig` VM
  backstop (issue 08).
- **Swap off by default (`memory_swap = memory`).** The original incident
  killed the VM by swap thrashing, not by OOM — the OOM kill was the
  relief, not the harm. Docker footgun: `--memory` without
  `--memory-swap` silently grants 2× (measured), so both flags are always
  passed.
- **The limit kills a process, not the Project.** The kernel picks the
  OOM victim by its `oom_score` heuristic — observed on the target host
  as the largest process, with PID 1 surviving and the session and DinD
  databases living on — but that is a heuristic, not a guarantee. All
  wording (ADR, notifications, docs) must say "kernel-selected victim
  (observed: largest process)", never promise PID 1 survival. Docker
  does not expose `memory.oom.group`.
- **Kernel log is the source of truth; `.State.OOMKilled` is a lifetime
  flag.** Measured: the flag reads true after a clean exit if any OOM
  kill happened during the container's lifetime, and false while the
  container keeps running after a kill — so live truth is
  `memory.events`, post-mortem detail is the dmesg-fed OOM archive.
  dmesg is shared across the WSL VM and readable without sudo on the
  host; a VM restart wipes it, hence archive-at-first-sighting.
- **`memory.high` is unreachable** (no Docker flag, cgroupfs mounted `ro`
  in-container, the cgroup tree lives in the `docker-desktop` distro).
  The 80/90 % Memory warning bands are the substitute, not a workaround.
- **No daemon.** Host side piggybacks on the invocation-time sweep
  (allow-for precedent); agent side is a PostToolUse hook with a ~1.4 ms
  silent path.
- **Config lives on the host (`resources.conf`), keyed by absolute path,
  never in the project repo** — sandboxed content must not configure its
  own sandbox; a hostile repo would simply raise its own limit.
- **Limit changes converge live via `docker update`** (measured on a
  running container); recreate and volume-preservation machinery is
  unnecessary.
